# 0014. The problem catalog

Date: 2026-11-25. Issue: SAN-119. PRD section 8.

## Context

Plans and the daily loop draw from a local table of problem metadata. The PRD's rules: seed files are generated by scripts in the repo and checked in; nothing is written from memory; statements are never stored; the app must not depend on LeetCode's unofficial endpoint at runtime.

## Decisions

1. **Three checked-in files, one per platform,** built by `npm run seed:catalog` (or `seed:leetcode`, `seed:cses`, `seed:codeforces`): `seed/catalog-leetcode.json` (3,332 free problems), `seed/catalog-cses.json` (the 400 tasks) and `seed/catalog-codeforces.json` (3,905 problems). One problem per line, in a fixed order, so diffs stay readable and a re-run on unchanged data rewrites nothing.

2. **Metadata only, enforced by the schema.** Each entry has platform, platform ID, display ID, title, URL, raw and normalized difficulty, the app's topics, the platform's tags and a solved count. The schema is strict: an entry with any other key is rejected, so statement text cannot ride along. The LeetCode query asks for list fields only and never for `content`.

3. **Sources.** Codeforces: the official API (`problemset.problems`). CSES: the public problem list page (no task pages). LeetCode: the unofficial GraphQL endpoint, used by the build script only; nothing under `src/` contacts it.

4. **Codeforces is limited to well-known problems:** programming problems with a rating and at least 9,000 solves. That keeps about 3,900; the script refuses to write a file outside 3,000 to 4,500, so a change at the source is noticed instead of shipped. LeetCode leaves out paid-only problems, which a user without a subscription cannot open.

5. **Pure transforms, thin scripts.** `src/platforms/catalog/<platform>.ts` turns a fetched listing into entries through the platform's adapter (IDs, URLs, difficulty, tags), so the catalog and the app cannot disagree about what a problem is. The scripts only fetch, call the transform, validate, report and write. The Codeforces transform can be reused by the app for a refresh on demand.

6. **Scripts never write a partial file.** Each request has a timeout and three tries; the result is validated and sanity-checked for size; the file is written to a temporary name and renamed. If a source cannot be reached the existing file is left untouched.

7. **Loading at launch.** `loadCatalogSeed` loads a file in one transaction, and only when its `generatedAt` is strictly newer than what `catalog_sources` records for that platform. A seed row is refreshed from the file; a row the user added by hand keeps what the user typed and only has empty fields filled; no row is ever deleted; a problem's `id`, `origin`, `starter_position` and `created_at` never change.

8. **A catalog file that cannot be loaded never stops the app from opening.** The catalog is reference data. `openDatabase` reports the problem (`catalogProblems`), main logs it, and the app opens with the user's data.

9. **Tags left unmapped on purpose.** A platform tag that fits none of the app's 25 topics stays in `sourceTags` and maps to nothing: for example LeetCode's Design, Database and Concurrency, Codeforces's interactive and `*special`, CSES's "Additional Problems". Forcing them into a topic would put the wrong problems in a plan.

10. **`solved_count` is only a hint of how well known a problem is,** used to rank search results and to prefer familiar problems as plan candidates. It is not shown as a statistic.

## Alternatives rejected

- **Fetching the catalog at first launch:** the app would need the network and LeetCode's unofficial endpoint at runtime, against the PRD.
- **All of Codeforces (about 11,500 problems):** most are obscure, and a plan should send people to problems with editorials and discussion.
- **A separate catalog table:** the PRD's data model has one `problems` table for catalog entries and user-added problems, and one table keeps attempts, cards and plans pointing at one kind of row.

## Limits

- Costs today: about 2.5 MB of JSON inside the main bundle, parsed at every launch; first launch on a fresh database shows Today in about 0.6 s.
- The scripts' error paths (timeouts, retries, the size window) are exercised by hand, not by automated tests.
