# ParaLeet

A Mac desktop app (Electron) that makes daily algorithm practice stick: a pixel-art parakeet is fed only when the user solves today's problem. The product spec is `docs/PRD.md` and it is canonical.

## Read first

1. `docs/STATUS.md`: where the build stands, what is in flight, blockers.
2. `docs/PRD.md`: what to build. Sections 2, 13 and 14 say how the work is run.
3. `docs/ARCHITECTURE.md`: module map and data flow.
4. `docs/decisions/`: why things are the way they are.
5. `docs/design-references.md`: the design contract for every screen.

## Charter (PRD section 2, in short)

- The codebase belongs to the lead agent. The owner does not review architecture and is not asked technical questions.
- Decide, write down why in `docs/decisions/`, and keep building. Never stop work to ask.
- Prefer boring, well-documented technology and few dependencies.
- Leave it working: tests pass, the app launches, changes are committed with clear messages.
- Verify your own work in the running app before calling it done.
- Report to the owner in product terms: what he can now do and how to try it.

Hard constraints that are never traded away:

1. The app runs entirely on the user's Mac. No hosted backend, no accounts, no server.
2. All user data stays in one local database file the user can back up by copying.
3. The app is fully usable with no LLM key. Only learning-plan generation needs one.
4. Problem statements are never copied or stored. Metadata and links only.
5. A second person can install it on another Mac from one file.

## Commands

```sh
npm install          # once
npm run dev          # launch the app with hot reload (data in ~/Library/Application Support/ParaLeet-dev)
npm run dev:ui       # the UI alone in a browser at http://localhost:5199, against the mock bridge
npm run check        # type check + lint + unit tests (run before every commit)
npm run test:unit    # unit tests; add a path to narrow: npm run test:unit -- src/core
npm run test:ui      # Playwright against the mock bridge; writes artifacts/screenshots/
npm run test:e2e     # builds, then runs the real Electron app end to end
npm run build        # production build into out/
npm run seed:starter # regenerate seed/starter.json from live LeetCode metadata
```

## Module map

| Folder | What it is | May import |
| --- | --- | --- |
| `src/core` | Pure TypeScript: days, streak, assignment policy, scheduler, pet facts, settings, topics, types. No Electron, database, network or system clock. Time is always an argument. | `zod`, `ts-fsrs` |
| `src/platforms` | One adapter per platform (LeetCode, CSES, Codeforces, Other) behind `PlatformAdapter`. | `core` |
| `src/data` | SQLite layer (`node:sqlite`), numbered migrations, seed loading, repositories. | `core`, `platforms` |
| `src/llm` | Learning-plan generation (M3). | `core` |
| `src/bridge` | The typed contract between UI and main: method list, zod input schemas, output types. | `core`, `zod` |
| `src/main` | Electron main process. `services/` is the Electron-free use-case layer; the rest is windows, timers and IPC. | everything except `ui` |
| `src/preload` | Exposes the bridge as `window.paraleet`. | `bridge/channels` |
| `src/ui` | React screens. Talks to the app only through `window.paraleet`. `mock/` is the in-browser stand-in for main. | `core`, `bridge` |
| `seed/` | Checked-in data files generated by `scripts/seed/`. | |
| `tests/ui`, `tests/e2e` | Playwright: mock-bridge UI tests, and real-app smoke tests. | |

These boundaries are enforced by ESLint (`eslint.config.js`). A lint error about a restricted import means the code is in the wrong module.

## Rules that bite

- **Time:** `core` never calls `new Date()` or `Date.now()`. Main passes `clock.now()` and `clock.timeZone()` in. Tests use `FakeClock`.
- **Schema:** change it only by appending a numbered migration in `src/data/migrations/` and adding a fixture to `src/data/migrate.test.ts`. Never edit a shipped migration.
- **Attempts are append-only** and are the source of truth. Stored streak and totals must equal `recomputePetFacts(attempts)`.
- **Bridge:** to add a method, add it to `src/bridge/channels.ts`, `src/bridge/contract.ts`, `src/main/services/index.ts` and `src/ui/mock/mockBridge.ts`. Inputs are validated in main.
- **UI:** use only the theme tokens in `src/ui/styles.css` and the shared components in `src/ui/components/`. Follow the screen's section in `docs/design-references.md`. Orange is the only accent.
- **Seeds:** never write problem lists from memory. Every entry comes from a fetched source through a script in `scripts/seed/`.
- **Secrets:** the API key is never written to the database, the repo or logs.
- **Dev data is separate:** `npm run dev` and tests never touch the installed app's data folder.

## How work is run (PRD section 13)

- The lead owns architecture, schema, `src/main`, `src/bridge`, shared UI components, Linear and every merge.
- Workers (`implementer` agent) take one Linear issue each, in their own git worktree and branch, and do not change interfaces, schema or dependencies without the lead's say.
- A fresh `reviewer` agent gives a verdict on each branch before it merges.
- Merge gate: type check, lint and all tests pass after rebasing on main; new behavior has tests; the lead has exercised the feature in the running app; every acceptance criterion is checked; the reviewer reports no blocking findings; docs are updated.
- Linear project "ParaLeet" (team `SAN`) tracks issues. If Linear and the PRD disagree, the PRD wins.

## Writing style for docs, issues and reports

Plain words, short sentences, product terms. Say what the user can now do and how to try it.
